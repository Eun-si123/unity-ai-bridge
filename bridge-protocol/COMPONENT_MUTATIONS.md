# Component add/remove contract

Phase 3 Component mutations build on the verified `component.inspect` identity/snapshot surface. They do not expose arbitrary reflection or arbitrary C# execution.

## `component.add`

MCP tool: `unity_add_component`  
Bridge risk: `write`

Required intent:

- `gameObjectGlobalObjectId` — exact active-scene GameObject identity,
- `typeName` — exact loaded concrete `Component` full name or assembly-qualified name,
- `expectedStateEpoch` + `expectedStateRevision` — fresh optimistic-concurrency token,
- `mutationId` — optional at MCP; generated by the Node bridge when omitted.

Unity resolves candidate types through `TypeCache.GetTypesDerivedFrom<Component>()`. The type must be concrete and unambiguous. The first add slice refuses `Transform` / `RectTransform` families rather than trying to replace the mandatory Transform.

The mutation executes on the Unity Editor main thread, adds through Unity Undo, marks the active scene dirty, then re-resolves the returned Component `GlobalObjectId`. Success requires native readback to confirm the exact Component identity, owning GameObject, and concrete type. If semantic verification fails, the common transaction reverts the Undo group and rollback verification requires the added Component identity to be absent.

A completed same-`mutationId` replay succeeds only while the exact added Component still exists with the completed owner/type identity. If the user Undoes the addition or otherwise removes/replaces it, replay fails closed with `stale_target/mutation_replay_stale`; it does not add another Component automatically.

## `component.remove`

MCP tool: `unity_remove_component`  
Bridge risk: `destructive`

Required intent:

- `componentGlobalObjectId` — exact Component identity, not a GameObject identity,
- `expectedStateEpoch` + `expectedStateRevision` — fresh optimistic-concurrency token,
- `mutationId` — optional at MCP; generated by the Node bridge when omitted.

The target must resolve directly to a Component whose GameObject belongs to the active scene. `Transform` / `RectTransform` removal is rejected in this slice.

Removal uses Unity Undo and verifies success by requiring the original Component `GlobalObjectId` to stop resolving. The operation result retains the removed type, owner, scene, and component-list index for verification/reconciliation. If the common transaction has to roll back, rollback verification requires the same Component identity to resolve again with the original owner, type, component index, and scene.

A completed same-`mutationId` replay succeeds only while the original Component remains absent. If Undo restores it, replay fails closed with `stale_target/mutation_replay_stale`; it does not remove the restored Component a second time.

`destructive` here means the operation removes Editor state. Unlike `scene.save`, the current Component removal path is Unity Undo-capable.

## Shared safety contract

Both mutations require:

- valid current state epoch/revision,
- active loaded scene,
- execution through the main-thread dispatcher,
- execution-boundary deadline enforcement,
- same-session mutation lifecycle and intent fingerprint,
- operation-specific native verification,
- replay protection after ambiguous delivery.

Current mutation persistence remains `SessionState`-scoped and does not survive a full Unity Editor restart.

## Initial verification type

The real Unity verifier uses `UnityEngine.BoxCollider`, which is a concrete built-in Component with no Transform replacement semantics. This does not imply that every possible third-party Component type has already been characterized.
