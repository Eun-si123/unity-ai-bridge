# Bounded Script Replace Contract

Status: **design/implementation slice in progress**

`script.replace` is the first Unity AI Bridge source-file mutation. It is intentionally narrower than generic filesystem editing.

## Scope

The first slice may replace the complete contents of **one existing `Assets/*.cs` Unity asset**.

It does not:

- create scripts,
- rename/move/delete scripts,
- edit `Packages/`,
- edit `.asmdef`, `.asmref`, `.rsp`, `.dll`, generated files, or arbitrary filesystem paths,
- execute arbitrary C#,
- claim Unity Undo for source-file persistence.

## Required observation

Call `script.read` / `unity_read_script` first and retain:

- canonical `path`,
- `guid`,
- raw-file `contentSha256`,
- encoding/BOM metadata.

The write requires the exact observed `path + guid + contentSha256` tuple. This is the compare-and-swap precondition.

## Inputs

- `path` — exact canonical existing `Assets/*.cs` path.
- `expectedGuid` — exact GUID from the prior Script read.
- `expectedContentSha256` — exact 64-hex raw-file SHA-256 from the prior Script read.
- `content` — complete desired source text.
- `mutationId` — same-session retry identity; generated by the MCP bridge when omitted.

First-slice replacement content is bounded to 128,000 UTF-16 code units and at most 512 KiB after strict UTF-8 encoding. The existing UTF-8 BOM presence is preserved automatically. Newline characters are not normalized: the supplied text determines them.

## Preconditions

Before any source bytes change, Unity must prove:

1. the Editor is not already compiling,
2. the Editor is not in or transitioning to Play Mode,
3. the path is an exact `Assets/*.cs` Unity asset,
4. the path resolves to a live `MonoScript`,
5. the canonical GUID equals `expectedGuid`,
6. the current raw-file SHA-256 equals `expectedContentSha256`,
7. the source is strict UTF-8 and no larger than the verified Script-read source bound,
8. `AssetDatabase.IsOpenForEdit` permits editing,
9. replacement text can be encoded as strict UTF-8 within the replacement bounds.

A stale GUID or stale raw SHA fails before mutation.

## At-most-once write and reload reconciliation

A source change can trigger AssetDatabase import, script compilation, assembly reload, domain reload, WebSocket disconnect, and reconnect. Those are normal lifecycle events for this operation.

The operation keeps an operation-specific SessionState journal before writing. The journal records the intent fingerprint, original GUID/SHA, intended new raw SHA, baseline compilation sequence, BOM/size metadata, and lifecycle stage.

Stages:

```text
prepared
  -> written
```

A repeated delivery with the same `mutationId` never blindly rewrites the file:

- `written` + current GUID/new SHA still match -> readback-only replay;
- `prepared` + current GUID/new SHA match -> reconcile as a completed write without rewriting;
- `prepared` + old SHA still present -> fail closed as incomplete; do not guess that re-execution is safe;
- any third GUID/SHA state -> fail closed as stale/ambiguous;
- same `mutationId` with different intent -> conflict.

SessionState does not survive a full Editor restart, but the mandatory old-content SHA still prevents a completed write from being blindly repeated after restart: the old SHA no longer matches.

## Persistence

The implementation writes replacement bytes to a sibling temporary file, flushes them, and uses an atomic file replacement primitive when supported. It then re-reads the target and requires the exact intended raw SHA before the journal advances to `written`.

The `.meta` file is not modified.

The write is a persistent filesystem mutation and is classified as `destructive` even though it is intended to be recoverable through source control or a later explicit recovery workflow.

## Import, compilation, and reload

After exact byte persistence is journaled, Unity requests import of the changed script. Unity's code-import pipeline may compile assemblies and reload the C# domain.

The MCP bridge treats persistence and compilation as separate outcomes. It uses the pre-write Diagnostics compilation sequence as a baseline, survives transient Editor disconnect/reconnect, waits for a later completed compilation snapshot, then performs a fresh `script.read` readback.

Terminal compile observations:

- `not_requested` — replacement was a no-op; no source bytes changed.
- `succeeded` — a later compilation completed with no compiler errors.
- `failed` — a later compilation completed with one or more compiler errors.
- `not_observed` — exact new bytes are persisted but a later compilation completion was not observed within the bounded wait. This is not permission to repeat the file write with a new mutationId.

A compiler error does **not** mean the source write failed. The result must keep the exact new file SHA and compiler diagnostics separate.

## Post-write verification

A successful/reconciled persistence result requires:

- same canonical path,
- same GUID,
- exact intended raw-file SHA,
- expected BOM behavior,
- exact encoded byte count.

After compilation observation/reconnect, the MCP layer performs a fresh Script read and again requires the same path/GUID/new SHA.

## Recovery policy

The first slice does not automatically restore the old source on compiler error. Automatic rollback would itself be a second persistent source mutation and another compilation/reload cycle, and could overwrite a concurrent human edit.

If persistence becomes ambiguous, refresh/re-read native file state first. Reuse the same `mutationId` only to reconcile the original intent. Choose a new mutation only from a fresh Script-read observation.

## Verification gate

Before this slice becomes Verified, tests must prove at minimum:

1. stale GUID/SHA reject without changing bytes,
2. exact CAS permits one intended write,
3. replacement byte readback yields the exact new SHA,
4. same-id replay does not perform a second file write,
5. a prepared journal can reconcile a confirmed new SHA after a simulated lifecycle interruption,
6. different same-id intent conflicts,
7. package paths are rejected,
8. strict UTF-8/BOM/bounds behavior is deterministic,
9. live MCP execution survives real compilation/domain reload/reconnect,
10. compile success and compile failure are reported separately from persistence success.
